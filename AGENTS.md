# Working on fiscal-sb

A Turborepo monorepo, scaffolded by create-ft-app 0.1.2, holding Laman, the FTDS website builder: the design is in `docs/laman.md`. This file is what you need to change it safely.

## Run it

Node 24.7 or later (see `.nvmrc`; it has the built-in argon2 the passwords use) and pnpm 12.16.1 (`packageManager` in `package.json`). From the repo root:

```sh
pnpm install
pnpm dev                         # every app in watch mode
pnpm build                       # every package, into git-ignored dist/ folders
```

- `pnpm dev` runs the server on :3000 and the admin on :3001/admin. The admin dev server proxies `/api`, `/render`, `/_astro`, `/media`, `/healthz`, `/docs`, `/openapi.json`, `/pagefind` and `/carian` to the server, so the browser sees one origin, as it does when the server serves the built admin. The published site is at :3000/. Connect MCP agents to :3001 in development: it proxies `/mcp`, `/oauth`, `/api/agents` and the OAuth `/.well-known` documents keeping its own Host, which the server writes its OAuth addresses from (`docs/mcp.md`).
- **The renderer is built, not watched.** The server imports `apps/renderer/dist`; after changing anything in `apps/renderer`, run `pnpm --filter @fiscal-sb/renderer build` (the dev server picks it up).
- **Settings are environment variables**, validated at boot in `apps/server/src/env.ts`; the server refuses to start with a clear message when one is wrong. Local values go in `apps/server/.env` (git-ignored; `.env.example` lists them all).
- **State is `DATA_DIR`** (`apps/server/data/` in development, git-ignored): `site.db` (SQLite, WAL) and `public/`, the published site. Delete the folder to start again; a new database starts with a home page.
- **Docker**: `Dockerfile` and `compose.yaml` at the root build and run the whole thing (guide: `docs/install-docker.md`). The image is `pnpm deploy` of the server, so a workspace package the server needs at run time must list everything it loads in its `files` (gitignored `dist/` is left out otherwise).
- **Backups** go to `BACKUP_DIR` (default `DATA_DIR/backups`): daily from the server, before every upgrade, and with `pnpm --filter @fiscal-sb/server cli backup`. Each is also copied off-site (S3-compatible storage, `src/offsite/`) when the super admin sets that up in Settings, which needs `BACKUP_SECRET_KEY`; `test/offsite-stores.test.ts` runs the real client against MinIO when `OFFSITE_TEST_S3` is set. Azure Blob Storage is written but parked, commented out, until a release can test it against real Azure (search for `Azure (parked)`). Restore is CLI-only (`cli restore <archive>`, server stopped). Never copy `site.db` while the server runs: see `docs/laman.md` § Backup and restore.
- **Ready check:** `GET /healthz` returns `{"ok":true}`. API docs (Scalar) are at `/docs`, the OpenAPI document at `/openapi.json`.
- Run one package with a filter, e.g. `pnpm --filter @fiscal-sb/server dev`.

## Rules that aren't obvious from the code

- **Versions live in the catalog.** Add a dependency to `catalog:` in `pnpm-workspace.yaml` and write `"<name>": "catalog:"` in the package.json. Don't put version ranges in package.json files. Renovate keeps the catalog current.
- **Workspace packages are `@fiscal-sb/<name>`** and referenced as `"workspace:*"`.
- **A new block touches three places:** its schema in `packages/blocks/src/blocks/` (listed in `registry.ts`, with its palette `group`, `icon` and the page `kinds` it may be placed on), its wrapper in `apps/renderer/src/blocks/` (listed in `Block.astro`), and almost nothing in the admin: the palette and property panel come from the registry. Two exceptions: a new palette icon (add it to `blockIcons` in `define.ts` and the type checker points at the admin's map), and BM for the block's English text (its name, description, field labels, help and options go in `apps/admin/src/i18n/messages/registry-ms.ts`, keyed by the English; `test/registry-i18n.test.ts` lists what's missing). The admin shows registry text through `rt()`. Field builders in `fields.ts` (`field.text`, `field.select`, `field.icon`, `field.media`, `field.toggle`, `field.page`, …) carry the panel metadata; an icon choice is `field.icon`, which the admin draws with its one `IconPicker` (`components/icon-picker.tsx`); text fields marked `inline` get a `<Field>` in the wrapper so they can be edited on the canvas. The registry test renders every block's defaults, and every template in `templates.ts`, through the schemas.
- **Pages have kinds:** `page`, `listing` (collects dated entries) and `entry` (an article under a listing). The API rejects blocks a kind can't use. Entries' fixed fields live in the draft (`PageDocument.entry`), so they publish and roll back with it.
- **Site settings and navigation are drafted documents** (`packages/contracts/src/site.ts`), like pages: saving writes the draft, publishing makes it live.
- **Site colours change only the `--_primary-*` primitives**, written by the layout from the `theme` document (`packages/blocks/src/theme.ts`, `docs/laman.md` § Site colours). Components keep using semantic tokens, so they follow; never hard-code a primary shade.
- **Block content is data, never HTML.** Links go through `Href` (no `javascript:`); rich text is Tiptap JSON written out by `richTextToHtml`, an allow-list.
- **Contract changes go everywhere at once:** the schema in `packages/contracts` or `packages/blocks`, the server route that uses it, and the admin code that reads it. The server turns the same Zod schemas into its OpenAPI document.
- **Only the API writes.** The admin changes content through `/api`; the canvas (`/render`) only reads.
- **Analytics live in their own database** (`DATA_DIR/analytics.db`, migrations in `apps/server/src/analytics/db.ts`). `POST /_v` is the one builder path the public site calls; it always answers 204. Nothing that identifies a visitor across days is stored: see `docs/analytics.md` before changing what's collected.
- **Agents use the API, not their own code paths.** An MCP tool (`apps/server/src/agents/tools.ts`) declares a permission like a route and does its work through `ctx.api`, which calls `/api` in-process as the officer with a one-time ticket, so the route's checks, validation, draft conflicts and audit apply. Never give a tool its own write path. See `docs/mcp.md`.
- **Every `/api` route declares who may use it:** `config: { access: "public" | "signedIn" | <permission> }`, with permissions and roles in `packages/contracts/src/auth.ts`. The server won't start with an `/api` route that doesn't. Hide what a role can't do in the admin with `useCan(permission)`; the server's check is what counts. See `docs/auth.md`.
- **A new install needs `SUPER_ADMIN_USERNAME` and `SUPER_ADMIN_PASSWORD`** to seed the first account; the server refuses to start without a super admin. Tests build the app signed in with `signedInApp` (`apps/server/test/helpers.ts`).
- **Drafts are saved from a version.** A page's `draftVersion` and a site document's `version` go back as the save's `base`, so someone else's save in between is refused (409 `draft_conflict`) rather than overwritten; the admin's page and site-document saves already send it. A new drafted document gets the same check (`conflictWith` in `apps/server/src/content/versions.ts`; a site document saves through `writeDraft` in `content/site.ts`). See `docs/laman.md` § Request flows.
- **Errors have one shape:** `{ "error": { "code": "snake_case", "message": "…" } }`; successful responses wrap their payload in `{ "data": … }`. Throw `new HttpError(status, code, message)` from `src/errors.ts`.
- **Routes declare Zod schemas** (`schema: { params: PageParams }`). Fastify validates with Zod (`src/validation.ts`), and the same schemas become the OpenAPI document.
- **Migrations are append-only** (`apps/server/src/db/migrations.ts`) and run on every start, after a snapshot that is put back if they fail. `0001_baseline` is 1.0; never squash again, and never reuse a name in `squashed` or `beforeBaseline`. Each release saves its database with `pnpm --filter @fiscal-sb/server fixture`, and every later build must boot and publish all of them (`test/upgrade.test.ts`).
- **Stored content must pass the current schemas after migrating**, or the server refuses to start. A schema change that saved content might not pass (a renamed or removed field, block or option, a tighter limit) ships with a migration that rewrites it with `rewriteDocuments`. A new kind of stored JSON goes in `storedDocuments` (`apps/server/src/db/documents.ts`). The schema snapshot in `test/upgrade.test.ts` fails on every schema change: decide whether a migration is needed, then update it with `-u`. See `docs/upgrades.md`.
- **The UI is built on [FTDS](https://mof-malaysia.github.io/ftds/llms.txt)** v0.2.2, with the renderer's registry at v0.2.6 for Page intro's primary wash and SiteSearch (Base UI, Tailwind v4). In the admin, add a component with `pnpm dlx shadcn@latest add @ftds/<name>` from `apps/admin`. In the renderer, the shadcn CLI can't install `.astro` files yet: use `pnpm ftds:add astro-<name>` from `apps/renderer` (or `apps/www`). Use FTDS before writing your own; build anything missing from FTDS tokens (`bg-bg-*`, `text-txt-*`, `border-otl-*`), never raw Tailwind colours or `dark:` overrides. Files under `src/components/ui`, `src/components/blocks`, `src/lib/ftds` and `styles/ftds.css` stay as the registry ships them (oxfmt and Oxlint skip them) so upgrades diff cleanly.
- **UI text goes through `t()`** with a key in `src/i18n/messages/en.ts`; the type checker rejects missing keys. Site content and the FTDS Astro labels are BM by default.
- **Never commit** `.env` files (only `.env.example`), `data/` or `.claude/`. Stage paths explicitly rather than `git add -A`.

## Before calling a change done

The pre-commit hook formats staged files and runs `pnpm check` (lint, type checks, tests); it is the project's gate, so don't bypass it with `--no-verify`. Before handing work over, also build:

```sh
pnpm format
pnpm verify                      # lint, check-types, test, build
```

For UI changes, also look at the result in a browser (`pnpm dev`).
